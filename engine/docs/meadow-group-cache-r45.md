# Meadow world-page cache, r45

Status: **experimental, default off, native only**. The first same-executable
off/on run completed and exercised the cache, but showed **no material reduction
in total GPU time**. Keep `KERN_MEADOW_GROUP_CACHE=0`; this result does not justify
a larger performance matrix or promotion. The implementation is a cache of
source-derived surface samples, **not a voxel field** and not completion of the
[world-volume plan](meadow-volume-field.md).

## Implemented scope

[meadow_group_cache.rs](../crates/render/src/meadow_group_cache.rs) groups 8 × 8
existing 0.45 m world cells. It shares up to 256 pages between views, with at most
four GPU page cooks per frame. Each page contains 64 × 64 orthographic samples
of the actual roots generated by the shared placement function: unlit material
and normal sums, revealage, nearest/farthest depth and pose displacement.
Page keys include world-group coordinates and quantized direction rather than
the complete camera matrix. Translation can reuse a page while the conservative
projection bound remains satisfied.

[meadow_group_gpu.rs](../crates/render/src/meadow_group_gpu.rs) produces these
samples from the existing directional source atlas. The consumer preserves raw
OIT sums and multiplies revealage; it does not reweight an averaged material by
the group's union alpha. Lighting remains the ordinary current-frame deferred
grass lighting. Unknown pages and opaque depth cutting through a group's depth
span retain the reference path. Camera shadows are unchanged.

This first implementation **still generates and submits every reference far
root quad**. A cached pixel can reject expensive reference atlas sampling, then
a page quad supplies its accumulated moments. It does not yet remove per-root
placement, vertex work or quad submissions. The `reference_roots_submitted`
counter reports these submissions, not actual fallback pixels. `active_pages`
means pages selected in a view's table, not pages proven to shade visible grass.

The current cache/reference motion transition is unresolved: a refreshed page
can refer to an older cached pose after intervening frames used reference
roots, and fallback can vary per pixel. `Renderer::set_upscale` explicitly rejects
DLSS while this cache is enabled. Static native validation must not be described
as temporal acceptance.

| Near, source grass render | 7.188 | 7.210 | +0.022 |
| Near, aggregate render | 0.040 | 0.051 | +0.010 |
| Near, aggregate placement | 0.032 | 0.032 | ~0 |
| Far, full GPU interval | 16.773 | 16.812 | +0.039 |
| Far, full GPU p95 | 17.504 | 17.371 | −0.133 |

| Far, aggregate placement | 0.051 | 0.052 | +0.001 |

The far aggregate pass is about 4.2% cheaper in this pair, but the full interval
does not improve. The source workload is unchanged: 1,272,480 triangles near and
4,556,000 far, counted once before the depth/colour submissions.

CPU work is separate. Main-thread encode/submit medians are 1.868 → 2.209 ms near
and 2.071 → 2.601 ms far. The eight captured page-planner observations have median
0.3297 ms overall: near median 0.3585 ms, range 0.3510–0.4356; far median 0.3001 ms,
range 0.2931–0.3084. These are sparse capture observations, not a continuous CPU
profile. They must not be added to the GPU interval. The original report's
disabled-cache summary collapses its zero cache serial to one observation;
analysis uses the actual capture frame IDs instead.

Cold page work is real and excluded from steady results only by the declared
warmup. Aggregate-placement time summed over frames 1–16 is 0.504 ms off versus
2.963 ms on. Over frames 193–208, after the camera cut, it is 0.821 versus
2.717 ms. These windows include normal placement and scheduling noise, so their
difference is not an isolated page-cook measurement. First-frame placement on is
0.291 ms near and 0.538 ms after the cut. All captured cache states already have
zero cooks/deferred requests; they do not show a moving-world update rate.

## Residency is not useful coverage

| Captured camera | Requested / active pages | Resident pages | Reference far roots | Added page triangles per pass |
| --- | ---: | ---: | ---: | ---: |
| Near | 38 / 38 | 38 | 0 | 76 |
| Far | 16 / 16 | 54 | 44,743 | 32 |

Every captured request is a hit, with zero deferred requests or evictions.
That **100% hit fraction is not 100% visible-grass coverage**. Near pages can be
selected even when no reference far root survives GPU culling. The CPU request
stage uses coarse terrain bounds, a broad view cone and projection/range gates;
it does not consume actual habitat occupancy or current-frame Hi-Z visibility.
It can therefore cook empty or occluded groups. Here all four near image pairs
are identical despite 38 active pages.

Far's sixteen groups contain at most 1,024 candidate cells, only **2.29%** of
44,743 submitted reference roots, before habitat, occlusion and pixel fallback
reduce useful coverage further. This is an upper bound on corresponding root
membership, not a measured replaced-pixel fraction. Root submissions remain
44,743 with the feature enabled. No per-pixel cache/fallback counter currently
establishes how much atlas sampling was eliminated.

Eligibility is restrictive by construction: the entire group support must lie
inside the far range, contain valid terrain, fit the broad view cone and satisfy
the 0.8 px projection/texel bound. Low resolution, terrain height span and padded
support can reject groups well before memory capacity is reached. Raising the
256-page cap would not address this measured case: peak residency is only 54.

Observed added allocations are **34,103,452 GPU bytes (32.524 MiB)** and
**1,577,472 CPU terrain-bound bytes (1.504 MiB)**. GPU bytes include the fixed page
atlas, producer scratch and explicitly counted buffers; they are not total VRAM
or allocator overhead. The original per-view root pools and render targets
remain allocated. No resource-saving claim follows from low page draw counts.

## Review of all sixteen previews

All off/on images at frames 32, 64, 128, 192, 224, 256, 320 and 384 were viewed.
No obvious new rectangular halo, bare hole, displaced road edge or changed tree
silhouette was visible at preview resolution. Near grass remains dense with
the same coarse 120-blade appearance; all four near off/on JPEG pairs are
byte-identical and decode identically. The far road view retains its existing
grass/verge edges, tree shadows and smooth distant hillside appearance.

Far off/on decoded mean absolute RGB differences are 0.0046–0.0053 on the 0–255
scale, p99 is zero, and maximum channel difference is 9–11. Between different
far captures within the reference run, mean differences are already
0.0049–0.0051 with maxima 9–10. This comparison does not attribute every changed
pixel to the cache and is not raw render-target parity: these are JPEG previews.
The small eligible area also weakens the test's power to expose page artifacts.

Fixed camera and fixed wind cannot establish absence of motion trails,
disocclusion holes or stale-pose transitions. No moving-camera, animated-wind,
four-view GPU or DLSS acceptance is claimed.

## Decision and next prerequisite

Keep the candidate **off** and retain this bounded native proof as evidence of
the producer/consumer and residency plumbing. Do not extend the matrix merely
because the cache reports hits. Before more performance runs, the design needs
observable useful coverage and actual removal of redundant member work, while
preserving terrain/depth fallback and optical bounds. Page requests should avoid
known empty/hidden work; page payload/eligibility must cover a meaningful share
without weakening quality gates blindly. Temporal representation transitions
need an explicit history/reactivity policy before the DLSS restriction can lift.

The 4K total output / four-player / 120 FPS target remains unmet. This first
surface-page cache neither closes that budget nor replaces the planned shared
world-volume architecture.
